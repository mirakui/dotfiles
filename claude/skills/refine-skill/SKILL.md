# Update Skill

このスキルは「あるスキルを実際に使って作業した直後に、その回で得た学びを元のスキルへ還元する」ための **メタスキル** です。
`save-as-skill` が "セッション → 新規スキル" を作るのに対し、これは "セッション → 既存スキル改善" の対になります。

スキルは「何度も再利用される手順書」です。1 回使うたびに必ず何かしらの摩擦 (手順が曖昧で解釈が割れた、edge case を踏んだ、ユーザに訂正された、逆に無駄なステップがあった) が見つかります。その学びをその場で還元しないと永遠に失われます。このスキルはその還元作業を構造化します。

会話履歴とユーザの好みに依存するため、**サブエージェントには委譲せず、メインエージェントが直接実行する**。履歴の機微 (どこで詰まったか、何を訂正されたか) はメインエージェントだけが知っているためです。

## Step 1: 更新対象のスキルを特定する

このセッションで実際に使った / 参照した / 言及されたスキルを会話履歴から推定する。手がかり:

- `Skill` ツールで起動したスキル
- `SKILL.md` を Read したパス
- ユーザが名前で言及したスキル
- 直前に `save-as-skill` で保存したスキル

推定したら、たとえ候補が 1 つでも `AskUserQuestion` (`header: "対象スキル"`) で「このスキルを改善対象にするか」を確認する。候補が複数あるときは選択肢として並べ、ユーザが Other で別スキルを指定できるようにする。**勝手に対象を決めて編集しない** — 違うスキルを書き換えると取り返しがつかないため。

対象が決まったら SKILL.md の絶対パスを特定する:

```bash
ls -d ~/.claude/skills/<name>/SKILL.md "$(pwd)/.claude/skills/<name>/SKILL.md" 2>/dev/null
```

注意: `~/.claude/skills` がユーザの dotfiles (例: `~/src/dotfiles/claude/skills`) へのシンボリックリンクになっていることがある。その場合 user スコープのスキルを編集すると結果的に dotfiles リポジトリに反映される。これは想定通りの挙動。

## Step 2: 対象スキルの現状を読む

特定した SKILL.md を `Read` で読み込む。**編集前に必ず全文を読むこと** — 既存の良い部分・意図的な書きぶりを壊さないため、また Step 5 で正確な `Edit` を行うために原文が必要。

## Step 3: セッションを振り返って改善材料を抽出する

今回このスキルを使った作業を最初から見直し、次の観点で改善材料を集める。これが後の差分の素材になる。

- **詰まり / 曖昧さ**: スキルの手順どおりに進めたが、記述が曖昧で解釈に迷った点、複数の進め方がありえてしまった点
- **訂正 / フィードバック**: ユーザからの「そうじゃなくて」「これは要らない」「こうして」。スキルに書いてあれば防げた訂正は最優先の改善材料
- **未カバーの edge case**: スキルが想定していなかった入力・状況・エラーと、それに対して今回うまくいった対処
- **無駄足 / 過剰な手順**: スキルの指示に従った結果やらなくてよい作業をした、冗長だったステップ (これは "削る" 改善材料)
- **トリガーの過不足**: このスキルが発火すべきなのにしなかった / 不要なのに発火した。あれば `description` の更新材料になる

材料が 1 つも見つからない (今回スキルは完璧に機能した) 場合は、無理に変更を作らず、その旨をユーザに報告して終了する。意味のない差分を入れないため。

## Step 4: 改善の深さをユーザに確認する

`AskUserQuestion` (`header: "改善範囲"`) で、今回の更新を **軽量更新** にするか **本格リライト** にするかを毎回確認する。判断しやすいよう、Step 3 で集めた改善材料の要点も一緒に提示する。

- **軽量更新**: 今回の学びを既存構造の中に反映する。詰まった箇所の補足、edge case の追記、無駄足ステップの削除、トリガー追加など。最も多いケース。
- **本格リライト**: 構造から見直して全面的に書き直す。スキルが根本的に的を外していたときだけ選ぶ。既存の良い部分を壊すリスクとコストが大きいので、ユーザが明確に望むときに限る。

## Step 5: 改善方針 — 1 セッションへの過適合を避ける

スキルは「これから何百回も別々のプロンプトで使われる」ものです。今回の 1 例だけに最適化すると、その例でしか動かない使えないスキルになります。改善案を書くときは次を徹底する:

- **一般化する**: 「今回の特定のファイル名・特定の値」ではなく、同種の状況一般に効く形に抽象化して書く
- **Why を添える**: 「なぜそのステップ / 注意が必要か」を 1 行入れる。理由が分かると、LLM は次回以降の別の edge case でも正しく判断できる
- **fiddly な MUST を増やさない**: `ALWAYS` / `NEVER` を多用したくなったら黄信号。どうしても外せないルールにだけ使い、それ以外は理由とともに柔らかく書く
- **lean に保つ**: 追記ばかりでなく、今回「無駄足だった」と分かったステップは積極的に削る。長いスキルほど読み手が迷う
- **元のスタイルに合わせる**: 命令形・Step 構成・トーンを既存記述に揃える

本格リライトを選んだ場合も同じ原則を適用する。まずドラフトを書き、新鮮な目で見直してから提示する。

## Step 6: 差分を提示して承認を得る

書き込む前に、変更案をユーザに提示する。何をどう変えるかが一目で分かるように:

- **追加**: どのステップ / 節に、どんな内容を足すか (要点 + 該当する新規テキスト)
- **修正**: どこを before → after でどう書き換えるか
- **削除**: どのステップ / 文を、なぜ削るか
- **description 変更** (あれば): トリガー過不足への対応

提示したら `AskUserQuestion` (`header: "差分承認"`) で「この内容で書き込む / 修正してほしい / 中止」を確認する。修正指示が来たら反映して再提示する。**承認を得てから書き込む** — 意図しない上書きを防ぐため。

## Step 7: 書き込みと報告

1. 承認された変更を `Edit` で対象 SKILL.md に反映する。原文の一部を差し替える形が基本なので `Edit` を使う。全面リライトなど変更が広範な場合のみ `Write` で全文を置き換える (`cat` / `echo` / heredoc は使わない)。
2. 完了したら次のフォーマットで報告する:

```
## Updated skill
- **Name**: <name>
- **Path**: <絶対パス>
- **Mode**: <軽量更新 | 本格リライト>
- **Changes**: <変更点を箇条書きで 2-4 個。追加/修正/削除を明示>
- **Next steps**: 新しいセッションでこのスキルを使い、改善が効いているか確認する
```

## 注意

- このスキルは会話履歴を読み取って改善材料を見抜く作業なので、サブエージェントには委譲しない。メインエージェントが直接判断する。
- git へのコミットはこのスキルの責務に含めない。コミットしたい場合はユーザの指示に従い `git-commit` などの別スキルに任せる。
- 改善対象が見つからない / 今回の学びが本当に一般化できない場合は、無理に書き換えず正直にその旨を報告する。スキルを「育てる」ことが目的であって、変更を出すこと自体が目的ではない。
- ユーザが対象スキル名を依頼文で明示している場合 (「<名前> を更新して」) は Step 1 の自動検出より優先し、AskUserQuestion ではそれを recommended として出す。
