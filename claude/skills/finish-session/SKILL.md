# Finish Session

このスキルは作業セッションを締めくくるための end-of-session ワークフロー。
今のセッションでユーザが何を達成したかったのか、それに対して何をやったのかを要約して提示し、
ユーザから終了理由をヒアリングしたうえで、残タスクがあれば Linear Issue として残し、
セッションで得た再利用可能な知見を wiki に記録する。

会話履歴とユーザの判断に強く依存するため、サブエージェントには委譲せず、メインエージェントが直接実行する。会話の文脈を持っているメインエージェントだけが、ゴール・残タスク・得られた知見を正確に言い当てられるため。

## Step 1: セッションを振り返って要約する

会話の最初から現在までを読み返し、次の2点を整理する。これがユーザに最初に見せる要約になる。

- **ゴール (Goal)**: このセッションでユーザが達成したかった中核的な目的は何か。1〜数行で言い切る。途中で目的が変わった/追加された場合は、その変遷も書く。
- **行ったこと (What was done)**: ゴールに対して実際に何をやったか。完了したこと・確認できたこと・まだ途中のことを区別して箇条書きにする。

次のフォーマットで表示する:

```markdown
## セッションの振り返り

### 🎯 ゴール
<ユーザが達成したかったこと>

### ✅ 行ったこと
- <やったこと / 完了状況>
- ...

### 🚧 未完了・気になっている点（あれば）
- <まだ終わっていないこと>
```

要約は推測で埋めず、実際の会話に基づいて書く。ゴールが曖昧なまま終わったセッションなら「ゴールが明示されなかった」と正直に書く。後続ステップの残タスク抽出はこの要約を土台にするので、ここで未完了点を取りこぼさないことが重要。

## Step 2: 終了理由をヒアリングする

`AskUserQuestion`（askme skill に準拠）で、セッションを終了する理由を1問たずねる。選択肢は次の3つ:

- `目的を果たせた` — セッションの目的を達成できたので終了する。
- `果たせなかったがキャンセル` — 目的は果たせていないが、ここで打ち切る。
- `一部達成・残タスクあり` — 目的の一部は果たした。まだ残タスクがある。

`header` は12文字以内（例: `終了理由`）にし、質問文・選択肢・説明はすべて日本語で書く。終了理由はユーザの主観的判断なので、必ずこのツールで本人に選んでもらう（こちらで決めつけない）。

## Step 3: 終了理由に応じて分岐する

残タスクの Linear 登録（Step 4-5）は「一部達成」のときだけ行う。一方、wiki への知見記録（Step 6）は **終了理由に関わらず常に** 行う。各ケースの流れ:

### 「目的を果たせた」の場合
完了をねぎらい、セッションを締める。Linear Issue は作らない。Step 6（wiki 記録）→ Step 7（報告）へ進む。

### 「果たせなかったがキャンセル」の場合
打ち切りを受け止め、簡潔に締める。Linear Issue は作らない。残タスク登録は「一部達成」のときのみ行う方針のため。Step 6（wiki 記録）→ Step 7（報告）へ進む。

### 「一部達成・残タスクあり」の場合
Step 4 へ進み、残タスクを Linear Issue として残す。その後 Step 6（wiki 記録）→ Step 7（報告）へ進む。

## Step 4: 残タスクを洗い出して提案する（一部達成の場合のみ）

Step 1 の「未完了・気になっている点」と会話全体を踏まえ、残タスクを具体的なアクション単位に分解する。各タスクについて次を用意する:

- **タイトル**: 何をするかが一目でわかる、動詞始まりの短い表現
- **説明**: 背景・現状・次の一手。なぜ残っているのか、何から着手すべきか
- **優先度の目安**（任意）

提案した残タスク一覧を表（タイトル / 概要 / 優先度）で提示し、`AskUserQuestion` で「この内容で Linear Issue を作るか」を確認する。選択肢の例:

- `この内容で作成` — 提案どおり Issue を作る
- `修正してから作成` — タスクの追加/削除/編集を聞いてから作る
- `作成しない` — Issue を作らずに終える

確認を取ってから作成に進む。会話から推定した残タスクが的外れなこともあるため、誤った Issue を量産しないよう必ず承認をはさむ。

## Step 5: 登録先を選んで Linear Issue を作成する（承認された場合のみ）

1. Linear MCP の `list_teams`（必要に応じて `list_projects`）でチーム/プロジェクト一覧を取得する。
2. `AskUserQuestion` で、どのチーム（必要ならプロジェクト）に登録するかをユーザに選ばせる。候補が多い場合は、それらしいもの／直近のものを上位2〜4件に絞って提示し、Other で自由入力できるようにする。登録先は実行時のコンテキストで変わるので固定せず、毎回ここで選んでもらう。
3. 確定した登録先に対し、Step 4 で承認された各残タスクを Linear MCP の `save_issue` で作成する。1タスク = 1 Issue。
   - タイトルと説明（Markdown）を渡す。説明にはこのセッションの文脈（何をやって、どこで止まっているか、次に何をすべきか）を含め、後から読んだ人がコールドスタートで着手できるようにする。

> Linear MCP のツール名は `list_teams` / `list_projects` / `save_issue`。MCP サーバ名のプレフィックス（UUID）はセッションごとに変わるため、ツール名のサフィックスで判断する。

## Step 6: セッションの知見を wiki に記録する（全終了理由で実行）

終了理由に関わらず、このセッションで得た再利用可能な知見を wiki に記録する。記録ロジックは `update-wiki` skill に集約されているので、**`update-wiki` skill を Skill ツールで呼び出して** 行う（手順を二重管理しないため）。

- 呼び出す前に、要約（Step 1）と会話全体から「今回新しく理解したこと・次に活かせる知見」を念頭に置く。`update-wiki` はそのセッション文脈をもとにページを作成/更新する。
- この wiki は「AI が自発的に更新してよい」領域なので **事前確認は不要**。`update-wiki` が `~/.claude/wiki` に直接書き込み、`INDEX.md` / `LOG.md` も更新する。結果は Step 7 でまとめて報告する。
- 記録に値する知見が無いセッション（雑談のみ、ごく短い作業など）では、`update-wiki` 側がスキップ判断する。空ページは作らない。

`update-wiki` が記録/更新したページ（new / updated）を、Step 7 の報告に含める。

## Step 7: 結果を報告する

```markdown
## セッション終了

- **終了理由**: <選択された理由>
- **作成した Linear Issue**:
  - [<Issue識別子>] <タイトル> — <URL>
  - ...
- **wiki に記録した知見**:
  - `<category/slug.md>` — <1 行サマリ>（new / updated）
  - ...
```

Linear Issue を作らなかった場合（達成 / キャンセル / 「作成しない」を選択）や、wiki に記録すべき知見が無かった場合は、その旨だけ簡潔に報告する。

## 注意

- このスキルは会話履歴を読んで自然言語で要約・分解する作業なので、サブエージェントに委譲せずメインエージェントが直接行う。
- 残タスクの Linear 登録は **「一部達成・残タスクあり」を選んだときのみ**。「キャンセル」では残タスクがあっても登録しない（ユーザ方針）。
- Linear Issue は **必ずユーザの確認を取ってから** 作成する。確認なしで作らない。
- Linear MCP が利用できない環境では、無理に登録しようとせず、残タスクをその場で Markdown のチェックリストとして提示し、登録は手動で行うよう案内する。
- wiki への知見記録（Step 6）は **終了理由に関わらず常に** 検討する。ただし記録に値する知見が無ければスキップしてよい。
- 扱いの違いに注意: **wiki は事前確認なしで自発的に書く**（wiki CLAUDE.md がそれを許可）。一方 **Linear Issue は確認必須**。
- wiki の保存先は常に `~/.claude/wiki` に固定。更新手順はその dir の `CLAUDE.md` を source of truth とし、本スキルの要約と食い違う場合は CLAUDE.md を優先する。ページ作成・更新時は `INDEX.md` への 1 行追加と `LOG.md` への追記を必ずセットで行う。
